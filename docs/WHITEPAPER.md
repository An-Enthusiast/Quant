# Real-Time Options Market Making & Non-Linear Risk Hedging Engine

### Technical Whitepaper — NSE Nifty & BankNifty Options

---

## 1. Abstract

This document describes the design, mathematical foundations, and measured
performance of a modular options market-making and risk-hedging engine
built for NSE index options (Nifty, BankNifty). The system combines a
low-latency C++ pricing/calibration core (Newton-Raphson Black-Scholes
implied vol, SVI surface fitting) with a Python orchestration layer
(Avellaneda-Stoikov quoting, an XGBoost order-flow toxicity overlay,
multi-asset non-linear risk aggregation, automated delta hedging, and an
event-driven backtester), all sitting behind a single `MarketDataInterface`
abstraction that lets the data source move from a zero-cost polling
prototype to a live broker websocket feed without touching any pricer,
alpha, or risk code.

**Scope note on data provenance.** This build was developed without live
NSE market access. Every ingestion, calibration, and backtest result in
this document is computed against either (a) a synthetic-but-internally-
consistent option chain generated by pricing a parametric skew through
this project's *own* Black-Scholes engine
(`data/sample_data/generate_fixtures.py`, `backtest/synthetic_ticks.py`),
matching `nsepython`'s real JSON schema exactly, or (b) that same synthetic
data replayed through DuckDB. The `NSEPythonAdapter` that talks to real
`nseindia.com` is fully implemented and unit-tested against the schema, but
no live pull has been made yet. Every number below should be read as
"the pipeline works end-to-end and produces internally-coherent output,"
not as a claim about real Nifty/BankNifty market behavior. See §9 for the
rollout plan to live data.

## 3. Data Ingestion Strategy

### Phase 1 — zero-cost prototyping

`core.nse_python_adapter.NSEPythonAdapter` wraps
`nsepython.nse_optionchain_scrapper(symbol)`, which hits NSE's public
`option-chain-indices` JSON endpoint — no API key, broker account, or paid
subscription required. The adapter normalizes NSE's raw schema
(`records.data[i].{CE,PE}.{lastPrice,bidprice,askPrice,bidQty,askQty,
openInterest,changeinOpenInterest,totalTradedVolume,impliedVolatility}`)
into the project's own `OptionContract`/`OptionChainSnapshot` dataclasses
(`core/option_chain.py`). A `use_fixture=True` constructor flag swaps the
live HTTP call for a recorded/synthetic JSON file of the exact same shape
(`data/sample_data/*.json`), so every downstream component — ingestion,
SVI fitting, quoting, backtesting — is exercised identically whether or not
live network access to `nseindia.com` is available.

### Phase 2 — live streaming (scaffolded, not implemented)

`core.shoonya_ws_adapter.ShoonyaWebSocketAdapter` and
`core.upstox_protobuf_adapter.UpstoxProtobufAdapter` implement the same
`MarketDataInterface` ABC. Both `connect()` methods currently raise a
`NotImplementedError` with a pointer to exactly what remains: the broker
login/OAuth handshake, instrument-token subscription, and the
tick-schema → `OptionContract` mapping (documented in each module's
docstring). Because both adapters honor the same interface as
`NSEPythonAdapter`, switching `main.py --mode live --broker shoonya` in
requires **zero** changes to `core/pricer_bindings.py`,
`alpha/quote_engine.py`, `risk/*`, or `backtest/*`.

### DuckDB storage

`data/schema.sql` defines a single append-only `option_chain_snapshots`
table (one row per timestamp/expiry/strike/option_type quote), indexed on
`(symbol, ts)` and `(symbol, expiry)`. `data/duckdb_store.py` batches
inserts through a pandas DataFrame → `duckdb`'s native DataFrame scan
rather than row-by-row `INSERT`, and every query pushes its filter
predicate down into DuckDB — the store never buffers more than one
snapshot's rows in memory on write, and never materializes more history
than a caller actually asks for on read, which is what "without memory
bottlenecks" means in practice for a columnar OLAP engine like DuckDB.

## 4. Module A — Volatility Surface & Fast Pricing Pipeline

### 4.1 Black-Scholes pricing and Greeks

Standard Black-Scholes-Merton with continuous dividend/carry yield `q`
(`csrc/src/bs_pricer.cpp`, mirrored in `core/greeks_numba.py`):

```
d1 = [ln(S/K) + (r - q + σ²/2)T] / (σ√T)
d2 = d1 - σ√T

C = S e^(-qT) N(d1) - K e^(-rT) N(d2)
P = K e^(-rT) N(-d2) - S e^(-qT) N(-d1)
```

Greeks follow from the standard closed forms (Delta, Gamma, Vega shared
between call/put by put-call-parity symmetry; Theta and Rho differ by
sign/term structure). Implemented once in C++ and once, formula-for-formula
identical, in Numba — see §4.4.

### 4.2 Newton-Raphson implied volatility, with a safeguard

Given a quoted price `P_mkt`, solve `BS(σ) = P_mkt` via:

```
σ_{n+1} = σ_n − (BS(σ_n) − P_mkt) / vega(σ_n)
```

**The safeguard.** Vega collapses toward zero for deep ITM/OTM strikes and
very short-dated contracts, at which point the Newton step
`Δσ = diff/vega` explodes and can diverge or oscillate outside `[0, ∞)`.
The solver (`csrc/src/bs_pricer.cpp::implied_vol`) checks `vega <
vega_floor` (default `1e-8`) at every iteration; the instant that trips, it
hands off the *remaining* iteration budget to bisection on `[1e-4, 5.0]`,
which is guaranteed to converge for any price inside the no-arbitrage
bounds `[intrinsic, S·e^{-qT}]` (call) / `[intrinsic, K·e^{-rT}]` (put) —
checked up front, so an out-of-bounds quote fails fast rather than chasing
an unreachable target. `tests/test_bs_pricer.py` and
`csrc/tests/cpp_tests.cpp` both cover the fallback path directly (by
forcing an unreachable `vega_floor`) as well as ordinary round-trip
recovery and put-call parity.

**Measured throughput** (single core, warm JIT/compiled binary — see §8
for the harness):

| Operation | Backend | Throughput | Latency |
|---|---|---|---|
| `bs_price` | C++ (`qengine`) | 3.56M calls/sec | 281 ns/call |
| `bs_price` | Numba fallback | 2.48M calls/sec | 403 ns/call |
| `implied_vol` (Newton+bisection) | C++ (`qengine`) | 1.17M calls/sec | 855 ns/call |

### 4.3 SVI surface calibration

Raw SVI parameterization of total implied variance vs. log-moneyness
`k = ln(K/F)` (Gatheral 2004):

```
w(k) = a + b·( ρ(k − m) + √((k − m)² + σ²) )
```

`csrc/src/svi.cpp` fits `(a, b, ρ, m, σ)` per expiry slice via a hand-rolled
Levenberg-Marquardt (numeric Jacobian by central differences, 5×5 normal
equations solved by Gaussian elimination with partial pivoting — no
external linear-algebra dependency). Two practical refinements were needed
to get a *well-posed* fit, not just a low-residual one:

1. **Data-adaptive initial guess** (`core/svi_surface.py::_initial_guess_from_data`).
   A single fixed seed (e.g. `a=0.02, b=0.15`) is badly scaled for
   short-dated slices where total variance can be an order of magnitude
   smaller, producing an ill-conditioned first Gauss-Newton step that gets
   stuck at a boundary-degenerate local minimum (`b → 0`). Seeding
   `a`/`b`/`m`/`σ` from the slice's own observed level, slope, and range
   fixes this.
2. **Domain-derived bounds on `(m, σ)`** (`csrc/src/svi.cpp::DomainBounds`).
   A smile that looks locally near-linear over the *observed* strike range
   (common for short-dated slices, where only a modest moneyness band is
   liquid) is under-identified — many `(b, ρ, m, σ)` combinations fit
   equally well by pushing the SVI vertex `m` far outside the data domain.
   Bounding `m` to (a margin around) the observed `k`-range and `σ` to a
   bounded multiple of its width — the standard practical-calibration
   guardrail (see e.g. Zeliade Systems' SVI calibration notes) — keeps the
   fit numerically well-behaved without changing what it's allowed to fit
   *within* the traded range.

**Static no-arbitrage checks** (`svi_check_butterfly`, `svi_check_calendar`,
Gatheral & Jacquier 2014):

```
Butterfly (per slice):  b ≥ 0,  |ρ| < 1,  σ > 0,
                         a + bσ√(1-ρ²) ≥ 0,     b(1+|ρ|) ≤ 4

Calendar (between expiries T1 < T2):  w(k; T2) ≥ w(k; T1)  for all k
```

Fitting each expiry slice independently (no joint cross-expiry constraint)
means calendar arbitrage is a *possible* outcome, not a structurally
excluded one — exactly why the check exists as a standalone, always-run
report rather than an assumption. In the synthetic surfaces used for
development, 1–2 of 2 calendar pairs typically pass; an occasional independent-fit
violation is realistic and is intentionally left visible in
`VolSurface.no_arbitrage_report()` rather than silently patched, so a
production deployment has a real signal to alert on or to feed into a
joint (rather than per-slice) calibration if it fires too often.

**Measured throughput:** 18.1 µs per slice fit (40 points, C++ LM), i.e.
~55,000 full-slice calibrations/sec on one core — recalibrating the entire
Nifty *and* BankNifty surface (all expiries) is sub-millisecond.

### 4.4 Vectorized Greeks engine

`core/greeks_numba.py` provides `@njit(parallel=True)` array versions of
price/Greeks/IV (`vectorized_greeks`, `vectorized_price`,
`vectorized_implied_vol`) that price an entire option chain — every live
Nifty+BankNifty strike/expiry — in one parallel call via `numba.prange`,
rather than a per-contract Python loop. This doubles as the pure-Python
fallback for `core/pricer_bindings.py` when the compiled C++ extension
isn't built, so scalar callers get identical formulas regardless of
backend, and `risk/portfolio.py`'s full-portfolio Greeks aggregation always
goes through the batched path.

**Measured throughput:** a 500-contract full-chain Greeks refresh
(Delta/Gamma/Theta/Vega/Rho for every contract) completes in 25.6 µs —
about 19.5M contract-Greeks/sec.

## 5. Module B — Microstructure & Dynamic Quoting

### 5.1 Avellaneda-Stoikov reservation pricing

From Avellaneda & Stoikov (2008): a risk-averse (CARA utility,
risk-aversion `γ`) market maker holding inventory `q` in an asset with
`dS = σ dW`, facing exponential order-arrival decay
`λ(δ) = A·e^{-κδ}` in quote distance `δ`, has HJB-optimal:

```
Reservation price:   r(s, q, t) = s − q·γ·σ²·(T − t)

Optimal total spread: δ_a + δ_b = γσ²(T−t) + (2/γ)·ln(1 + γ/κ)
```

`alpha/avellaneda_stoikov.py` implements both directly, with the full
derivation sketch in the module docstring. `tests/test_avellaneda_stoikov.py`
verifies the textbook sanity properties directly: `r = s` at zero
inventory, `r` skews below `s` for long inventory / above for short, and
the spread widens monotonically with both `σ` and `(T−t)`.

### 5.2 Order-flow toxicity classifier

`alpha/toxicity_model.py::ToxicityClassifier` wraps XGBoost (primary,
`n_estimators=200, max_depth=4`) with a `RandomForestClassifier` fallback
if `xgboost` isn't importable — trained on four microstructure features
computed in `alpha/features.py`:

- **Order-flow imbalance**: `(bid_qty − ask_qty) / (bid_qty + ask_qty)`
- **Δ open interest**: change in OI since the previous snapshot
- **Spread velocity**: `d(ask − bid)/dt` between consecutive snapshots
- **Volume imbalance**: change in cumulative traded volume since the
  previous snapshot

**This project ships the full train/predict/save/load architecture, not a
trained model.** A real toxicity label (did a quote posted at the touch
actually get adversely selected shortly after?) needs substantial real
sequential order-flow history, which isn't available yet (see §1's scope
note). `tests/test_toxicity_model_plumbing.py` proves the pipeline
executes correctly on a synthetic sklearn dataset — that is a code-path
correctness check, explicitly not a claim of predictive validity.
`alpha/train_toxicity_model.py` is fully functional against real ingested
DuckDB history: it builds a forward-looking adverse-selection label (did
the mid price move against a passive quote by more than the quoted spread
within the next `horizon` snapshots?) and fails loudly with an actionable
message if fewer than `MIN_DISTINCT_TIMESTAMPS + horizon` snapshots have
been ingested, rather than silently training on too little data.

### 5.3 Quote engine: combining AS with inventory skew and toxicity

`alpha/quote_engine.py::QuoteEngine.quote_snapshot` produces final
bid/ask per contract as:

```
half_spread = AS_optimal_spread(γ, σ, T−t, κ) / 2 × min(1 + β·toxicity_score, widen_cap)
bid = round_to_tick(r − half_spread)
ask = round_to_tick(r + half_spread)
```

where `r` already embeds the inventory skew from §5.1 (via
`risk.portfolio.Portfolio.get_position`), `σ` comes from the SVI surface
(§4.3), and `toxicity_score` defaults to 0 for any contract without a
supplied score — so the quoting logic is fully functional standalone,
without a trained toxicity model wired in.

## 6. Module C — Portfolio Risk & Automated Hedging

### 6.1 Multi-asset non-linear risk aggregation

`risk/portfolio.py::Portfolio.compute_greeks` aggregates net
Delta/Gamma/Theta/Vega **per underlying** (Nifty, BankNifty independently,
plus a combined total available via `GreeksSnapshot.total(...)`) by
batching every open option position of a given underlying through
`core.greeks_numba.vectorized_greeks` in one array call, and adding
futures/underlying positions as pure unit-delta exposures. This is a
non-linear aggregation in the sense that matters for a market maker: Gamma
and Vega are position-size- and moneyness-dependent, so the portfolio's
risk profile is not a simple sum of static per-contract numbers — it's
recomputed from current spot/vol on every call.

### 6.2 Automated delta hedging

`risk/hedging_engine.py::compute_hedge_orders`: when
`risk/risk_limits.py::check_breaches` flags `|net_delta| > limit` for an
underlying, the hedge order sizes the futures trade to bring exposure back
to a **fraction** of the limit (`target_band_fraction`, default 0.5) —
not fully flat — to avoid over-trading (paying the futures bid-ask spread
and slippage on every small oscillation around the limit). Only delta
breaches generate a futures hedge: futures are a pure-delta instrument
(zero Gamma/Vega), so a Gamma or Vega breach is surfaced by
`check_breaches` for the desk to act on via the *options* book (a futures
trade structurally cannot fix it). Estimated hedge cost combines a
one-way futures half-spread and a linear market-impact slippage term
proportional to trade size (`backtest/execution_sim.py::aggressive_fill_price`
for the execution side).

## 7. Module D — Event-Driven Backtester

### 7.1 Fill model

NSE's public option-chain snapshot (what `NSEPythonAdapter` — and this
session's synthetic generator — produce) reports touchline best-bid/ask +
resting quantity, not a full L3 order-book tape. `backtest/order_book.py`
therefore uses a standard simplified snapshot-driven fill model rather than
a textbook FIFO queue simulator: a resting quote **fully fills** the
instant the market's touch crosses through its price (exact, not an
approximation), and **partially fills**, proportional to observed
contract-level traded-volume delta net of an estimated queue-ahead
quantity, when it sits exactly at the touch without being crossed. This
queue-ahead estimate is captured at quote-post time from the
exchange-reported resting size at that price (zero if the quote
price-improves the current touch). `backtest/execution_sim.py` separately
models aggressive (market) fills for the hedging engine's futures orders —
half-spread plus linear market impact.

### 7.2 Event loop

`backtest/event_engine.py::BacktestEngine` replays a chronological,
multi-symbol stream of `OptionChainSnapshot`s: at each tick, quotes posted
at the *previous* tick are checked for fills against the current tick's
touch, the SVI surface is refit from the current chain, portfolio Greeks
are recomputed, any risk breach triggers a hedge order, the portfolio is
marked to market, and fresh quotes are posted for the next tick.

### 7.3 Data source: synthetic session generation

No live/recorded NSE tick history is available yet (§1), so
`backtest/synthetic_ticks.py::generate_tick_series` drives a GBM spot path
through this project's own pricer with a fixed parametric skew each tick,
with per-contract OI and cumulative volume evolving as their own small
random walks (not resampled independently each tick, since the feature
engineering in §5.2 depends on realistic monotonic-ish dynamics).
`backtest/run_backtest.py --source synthetic` generates such a session for
Nifty and BankNifty, **ingests it into DuckDB via the real ingestion path**
(`data.duckdb_store.DuckDBStore`), and only then replays it — exercising
the full ingest → DuckDB → backtest pipeline end to end.
`--source duckdb` replays whatever real history has already been ingested
(e.g. via `python -m data.ingest --mode live` once that's available)
through the identical code path.

### 7.4 Backtest results (synthetic session — read per §1's scope note)

180 ticks (~15 minutes at 5s/tick) per underlying, Nifty + BankNifty,
`max_net_delta = 300`:

| Metric | Value |
|---|---|
| Fills + hedge trades executed | 18 |
| Total P&L | 227.99 |
| Sharpe ratio (annualized) | 180.1 |
| Sortino ratio (annualized) | 311.2 |
| Max drawdown | −35.44 |
| Avg \|net delta\| | 2.30 |
| Max \|net delta\| | 8.56 |

**Read this table as a pipeline-correctness demonstration, not a claim
about strategy edge.** Two caveats specifically:

1. The P&L is generated against *synthetic* quotes/fills (§7.3, §1) — it
   says the mechanics (quoting → fills → hedging → mark-to-market →
   analytics) are wired correctly, not that this strategy is profitable on
   real Nifty/BankNifty flow.
2. The annualized Sharpe/Sortino figures are large in absolute terms
   because `periods_per_year` annualizes 5-second-bar returns by
   `√(NSE_session_seconds_per_year / 5)` — a standard formula, but one that
   mechanically inflates small-sample high-frequency Sharpe ratios. Treat
   the *relative* ordering (e.g. Sharpe vs. Sortino, or comparing two
   configs against each other) as informative; treat the absolute number
   as an artifact of the annualization convention over a 15-minute sample,
   not a real risk-adjusted-return estimate.

## 8. Module E — Production Engineering & Containerization

`deployment/Dockerfile` is a two-stage build: stage 1
(`python:3.11-slim` + `build-essential` + `cmake`) compiles `csrc/` via the
same CMake configuration used locally (`pybind11_DIR` resolved from
`python -m pybind11 --cmakedir`), producing `core/qengine*.so`; stage 2
copies only that compiled extension plus the application code into a clean
`python:3.11-slim` runtime image running as a non-root `quant` user, with
`/app/data/db` declared as a volume for DuckDB persistence.
`deployment/docker-compose.yml` mounts `./data/db` from the host and
defaults to `--mode prototype --fixture --max-polls 0` (a continuously
running, network-free demo).

**Verification status:** `cmake`/`ctest` were run directly (not just
inside Docker) and pass (§4). `docker compose config` was run and confirms
the compose file parses and resolves correctly. A full `docker build` was
attempted but could not complete on the current development machine: the
network here blocks the pull of the `python:3.11-slim` base image from
Docker Hub's CDN backend (`production.cloudfront.docker.com`), returning
an explicit `403` rather than a transient failure. The Dockerfile/compose
files are written and reviewed to the same standard as everything else in
this repository; building the image from a machine with normal Docker Hub
access is the one verification step not yet completed directly.

**Benchmark harness** (§4.2, §4.4, §4.3 numbers): single core, warm
compiled/JIT state, `time.perf_counter()` around tight loops of
200,000 (`bs_price`/`implied_vol`), 2,000×500-contract
(`vectorized_greeks`), and 500 (`svi_calibrate`) repetitions respectively;
see the benchmark script pattern in this document's §4 subsections for
exact parameters.

## 9. Limitations & Phase 2 Roadmap

1. **Live data.** `NSEPythonAdapter` is real and schema-tested. Two
   deliberately conservative live-pull attempts
   (`scripts/live_pull_smoke_test.py` -- one request, no retries, see
   that script's docstring for its safety properties) were made from two
   different machines:
   - From a network-restricted development machine, the outbound
     connection to `nseindia.com` was blocked entirely before any request
     reached NSE's servers -- a local network restriction, not an NSE
     anti-bot block.
   - From an unrestricted machine, `--diagnostic` mode (which reports each
     step's raw HTTP status/body instead of relying on `nsefetch`'s opaque
     wrapper) showed requests reaching NSE's real servers but being
     rejected by NSE's own edge: a `403` on the initial homepage request
     (no clean cookie handshake established) and a `404 Resource not
     found` on the option-chain API call itself, rather than JSON. This
     is a known, widely-reported characteristic of `nsepython`/NSE's
     anti-bot layer, not a bug in this codebase -- the adapter, parser,
     and ingestion path are otherwise fully exercised against the fixture
     schema (§3).

   `nsepython` remains useful for zero-cost local development against the
   documented schema (fixture mode) and may work intermittently depending
   on NSE's bot-detection posture at a given time, but should not be
   relied on as a production data source -- Phase 2's broker adapters
   (Shoonya/Upstox, §3) are the reliable path to live data. Next step if
   pursuing `nsepython` further: investigate session/cookie handling more
   closely (e.g. whether a real browser's TLS fingerprint or additional
   headers are needed), but treat this as a research spike, not a
   blocking dependency.
2. **Toxicity model training.** Once real sequential history exists,
   `python -m alpha.train_toxicity_model --symbol NIFTY` trains a real
   model from it; the label definition in that script's docstring is a
   reasonable default, not a validated-on-real-data choice — expect to
   iterate on it once real fills/adverse-selection outcomes are
   observable.
3. **Live broker adapters.** `ShoonyaWebSocketAdapter` and
   `UpstoxProtobufAdapter` need real credentials and the websocket/protobuf
   handshake implemented per their module docstrings; the
   `MarketDataInterface` contract they'll conform to is already fixed and
   tested against the Phase-1 adapter.
4. **Joint (cross-expiry) SVI calibration.** Current calibration is
   per-slice; the occasional calendar-arbitrage violation surfaced by
   `VolSurface.no_arbitrage_report()` (§4.3) would be structurally
   eliminated by a joint calibration that constrains later-expiry minimum
   variance to dominate earlier-expiry minimum variance during the fit
   itself, at the cost of a more complex (coupled, higher-dimensional)
   optimization.
5. **Order-book fidelity.** The backtester's fill model (§7.1) is a
   documented approximation appropriate to touch+volume data; real L2/L3
   depth from a live broker feed (Phase 2) would let the backtester graduate
   to genuine FIFO queue simulation.
6. **Docker image build.** Blocked on the current development machine by
   local network restrictions (§8), not by anything in the Dockerfile
   itself; verify with
   `docker build -f deployment/Dockerfile -t quant-engine .` from a
   machine with normal registry access.

## 10. Setup Guide

```bash
# 1. Clone and enter the repo, create a virtualenv
git clone <repo-url> && cd Quant
python3 -m venv .venv && source .venv/bin/activate
pip install --upgrade pip && pip install -r requirements.txt

# 2. Build the C++ pricing/SVI engine
cmake -S csrc -B csrc/build -DCMAKE_BUILD_TYPE=Release
cmake --build csrc/build -j"$(nproc)"
# -> produces core/qengine*.so; core/pricer_bindings.py auto-falls back to
#    the pure Numba engine if this step is skipped.

# 3. Run the test suite (Python + C++)
pytest -q
(cd csrc/build && ctest --output-on-failure)

# 4. Ingest a chain snapshot (fixture mode -- no live NSE call)
python -m data.ingest --mode fixture --symbols NIFTY,BANKNIFTY

# 5. Run the prototype quoting loop against the fixture
python main.py --mode prototype --fixture --symbols NIFTY --max-polls 1

# 6. Run the event-driven backtest (synthetic session, ingested into DuckDB)
python -m backtest.run_backtest --source synthetic --n-ticks 180

# 7. (Once live NSE access is available) switch to live polling
python -m data.ingest --mode live --symbols NIFTY,BANKNIFTY --interval 5 --max-polls 0
python main.py --mode prototype --symbols NIFTY,BANKNIFTY --interval 5 --max-polls 0

# 8. Containerized deployment (from an environment with Docker Hub access)
docker compose -f deployment/docker-compose.yml up --build
```
